**An AI coding agent deleted PocketOS's production database because it held a key that could delete anything, and it guessed instead of checking.** According to founder Jer Crane, as [reported by Decrypt](https://decrypt.co/365897/ai-agent-deletes-startup-database-9-seconds-founder-says), a Cursor agent running Anthropic's Claude Opus 4.6 wiped the database and its volume-level backups in one API call to Railway, PocketOS's hosting provider. He says it took nine seconds.

One headline called it ["The machines are rising"](https://capeargus.co.za/technology/software-and-internet/2026-05-06-the-machines-are-rising--claude-ai-agent-deletes-all-company-data-in-nine-seconds-before-chilling-admission-of-guilt/). The evidence points somewhere duller: an unscoped API token, a delete with no undo, and an agent trying to finish its task.

## What happened

PocketOS sells software that car rental operators use for reservations, payments and vehicle tracking. The agent was working in staging, a test copy of the system, when it [hit a credential mismatch](https://www.theregister.com/2026/04/27/cursoropus_agent_snuffs_out_pocketos/). It decided to fix that by deleting a Railway volume.

To do it, the agent found an API token in an unrelated file. The Register and [Zenity](https://zenity.io/blog/ai-agent-database-deletion-pocketos) report it was made for adding and removing custom domains. It could do far more. Railway's [own account](https://blog.railway.com/p/your-ai-wants-to-nuke-your-database) says the token "was provisioned with account scoped access, the maximum access possible."

The delete did not stay in staging. It hit the production database, and Railway kept volume-level backups in the same volume. One call removed both.

## The confession is not the evidence

When Crane asked the agent why it had done this, it wrote what he called a confession. Decrypt and The Register both quote it: "I guessed that deleting a staging volume via the API would be scoped to staging only." It said it had not checked whether the volume ID was shared across environments. It admitted Crane never asked it to delete anything.

Read that as a description of a process, not a guilty mind. The text was produced on request, after the fact. What it describes is a system that pursued a fix with the tools in reach and skipped verification. That is obedience to the task, carried out badly.

It also shows why written rules are weak protection. The agent could quote its rule against destructive commands and still break it. A rule in a prompt is advice to the model. A scoped token is a wall.

Railway's CEO, Jake Cooper, first told The Register the API worked as designed: "if you (or your agent) authenticate, and call delete, we will honor that request." Later he said the agent had reached a legacy endpoint that lacked the "delayed delete" logic the dashboard has.

## What changed because of it

Railway shipped a fix within days. Its [changelog for 1 May 2026](https://railway.com/changelog/2026-05-01-undoable-deletes) says `volumeDelete` used to remove volumes "immediately, with no recovery path", and that API deletions now soft-delete for 48 hours. Its blog adds that backup deletion is delayed too, and that it will review how users pick token scopes.

The changelog puts the lesson in one line: "A human hesitates before a bad command. An agent calls the next tool."

Crane did not let himself off either. The Register reports he blamed Cursor's and Railway's "failures (plural)" while accepting his own part in exposing a production API key.

## Where the sources disagree

- **Did PocketOS get everything back?** Railway says the customer "is back up with all their data". [Tom's Hardware](https://www.tomshardware.com/tech-industry/artificial-intelligence/victim-of-ai-agent-that-deleted-companys-entire-database-gets-their-data-back-cloud-provider-recovers-critical-files-and-broadens-its-48-hour-delayed-delete-policy) says it was restored "apparently in full". Decrypt reports PocketOS restored operations from a three-month-old backup that Railway recovered, and that Crane said significant data gaps remain.
- **How long did recovery take?** Cooper told Decrypt the data came back 30 minutes after he connected with Crane. He blamed the longer wait on a support ticket that lapsed for more than 24 hours.
- **Rogue or not?** Cooper himself called it a "rogue customer AI". The agent's own account describes a guess made while fixing a mismatch, not a goal of its own.

## The lesson for anyone running agents

The agent did not need to be clever to cause this. It needed a broad key and an API with no pause. Railway's post says it plainly: "An agent is working from an interpretation of a task, and that interpretation can drift."

So scope every token to the job it was made for. Keep backups outside the thing they protect. Put irreversible actions behind something the model cannot talk its way past. The model will follow the task. Your permissions decide how far.
